# 资源数据生成

blockstates、models/block、models/item、items 四类 JSON 全部由 datagen 产出，输出目录
`common/src/generated/resources/assets/minelzu/`，由 `common/build.gradle` 的
`sourceSets.main.resources.srcDir 'src/generated/resources'` 一起打包。
**不要手改生成的 JSON**，改 datagen 代码后重跑 `.\gradlew.bat :neoforge:runData`。
语言文件（`common/src/main/resources/assets/minelzu/lang/*.json`）不参与 datagen，仍然手写。

生成一份、两个加载器共用：Fabric 侧没有单独的 datagen 任务。

## 参与生成的两个提供器

| 提供器 | 文件 | 产物 |
| --- | --- | --- |
| `ModModelProvider` | `common/.../datagen/ModModelProvider.kt` | `blockstates/`、`items/`、`models/` |
| `ModBlockTagsProvider` | `common/.../datagen/ModBlockTagsProvider.kt` | `data/minecraft/tags/block/walls.json` |

两者都在 `neoforge/.../neoforge/ModDatagen.kt` 里通过 `GatherDataEvent.Client` 的
`createProvider(...)` 注册；`MineLZUNeoForge` 的构造器把 `GatherDataEvent.Client` 挂到
mod 事件总线。两个 provider 本身放在 `common`，只依赖 vanilla 的
`DataProvider` / `PackOutput` / `TagsProvider`，因此两个加载器都能编译。

## ModModelProvider 的结构

`common` 编译时用的是 vanilla 未打补丁的 jar，NeoForge 对 `ModelProvider` 的增强
（`registerModels`、`getKnownBlocks`、内部 collector）在 vanilla 里不存在，所以
`ModModelProvider` 直接实现 vanilla 的 `DataProvider`：

* `run(cache)` 里自己建 `BlockModelGenerators`，用三个收集器接住产物：
  方块状态（`Consumer<BlockModelDefinitionGenerator>`）、物品定义
  （`ItemModelOutput`）、模型文件（`BiConsumer<Identifier, ModelInstance>`）；
* 之后按 `PackOutput.Target.RESOURCE_PACK` 的三个子目录分别
  `DataProvider.saveStable(...)`：`blockstates/<方块>.json`（`BlockStateModelDispatcher.CODEC`）、
  `items/<物品>.json`（`ClientItem.CODEC`）、`models/<id>.json`；
* `BlockModelGenerators` 的 `blockStateOutput`、`itemModelOutput`、`modelOutput` 与
  `plainVariant`、`createSimpleBlock`、`createSlab`、`createStairs`、
  `ROTATION_HORIZONTAL_FACING` 在 vanilla 里是 private，通过
  `common/src/main/resources/minelzu.accesswidener`（`official` 命名空间）放宽；
  两个模块的 `loom { accessWidenerPath = ... }` 负责接线。

内部按四张表遍历：

| 表 | 含义 | 产物 |
| --- | --- | --- |
| `cubes` | 单一贴图的立方体（`minecraft:block/cube_all`） | 方块模型 + 单变体 blockstate + item |
| `glassBlocks` | cube_all 且 `"ambientocclusion": false` | 同上（tg_blue 用） |
| `shapedBases` | 有楼梯与台阶的基块 | 基块模型复用 cube 表，额外生成 `_slab`、`_slab_top`、`_stairs`、`_stairs_inner`、`_stairs_outer` 五个模型，以及 slab / stairs 的 blockstate 与物品模型 |
| `elementBlocks` | 自定义元素模型（Blockbench 转写） | `minecraft:block/block` 父模型 + 元素数组 + blockstate |

`TexturedBlock(path)` 里 `path` 形如 `bricks/ow_02_cube`：

* 模型 id = `minelzu:block/<path>`
* 纹理 id = `minelzu:block/<path>`（纹理文件放在 `textures/block/<path>.png`）
* `model(suffix)` 派生新模型 id，`withSuffix(suffix)` 派生新 `TexturedBlock`

物品模型统一走 `item()`：
物品模型 id 为 `minelzu:item/<注册名>`，同时写出
`models/item/<注册名>.json`（`parent` 指向方块模型）与
`items/<注册名>.json`（`{"model":{"type":"minecraft:model","model":"minelzu:item/<注册名>"}}`）。

同一个模型 id 在一次运行里只能写一次（收集器会报
`Duplicate model definition for ...`），所以每个模型都先算一次再复用返回的 `Identifier`。

### 朝向方块的 blockstate

元素方块用 `PropertyDispatch<VariantMutator>` 描述四个水平朝向的旋转：

```kotlin
val supportBarFacing = PropertyDispatch.modify(BlockStateProperties.HORIZONTAL_FACING)
    .select(Direction.NORTH, BlockModelGenerators.Y_ROT_90)
    .select(Direction.SOUTH, BlockModelGenerators.Y_ROT_270)
    .select(Direction.EAST, BlockModelGenerators.Y_ROT_180)
    .select(Direction.WEST, BlockModelGenerators.NOP)
```

`ElementBlock(block, elements, facing)` 的 `facing` 传 `null` 表示只有一个变体
（对应 `lamp_post`、`co_01`）；`a2_wall_lamp` 直接复用
`BlockModelGenerators.ROTATION_HORIZONTAL_FACING`（北 0°、南 180°、东 90°、西 270°）。

## 自定义元素模型的 DSL

`common/.../datagen/model/ElementModel.kt` 提供极小的 Kotlin DSL，
`common/.../datagen/model/ElementModels.kt` 则是六个 Blockbench 模型
（`a2_openwork`、`co_01`、`a2_wall_lamp`、`lamp_post`、`support_bar`、`ow_02`）
逐元素转写出来的数据。

```kotlin
val example: List<Element> = listOf(
    element(v(0.0, 0.0, 3.0), v(16.0, 16.0, 13.0)) {
        north(0.0, 0.0, 4.0, 4.0)
        east(0.0, 0.0, 4.0, 4.0)
        south(0.0, 0.0, 4.0, 4.0)
        west(0.0, 0.0, 4.0, 4.0)
        up(0.0, 0.0, 4.0, 4.0)
        down(0.0, 0.0, 4.0, 4.0)
    },
)
```

* `element(from, to, rotation = null) { ... }`：`from`/`to` 是 0–16 坐标；
* `rotation(x, y, z, "y", 45.0)`：轴的取值是 `"x"`、`"y"`、`"z"`；
* 六个面按 `north`、`east`、`south`、`west`、`up`、`down` 提供，参数是 uv 四元组；
* 生成的 JSON 里贴图键固定为 `#0`，`textures.0` 与 `textures.particle` 都指向方块纹理；
* Blockbench 的 `credit`、`groups`、`texture_size`、元素 `name` 属于编辑器元数据，
  渲染无影响，转换时已丢弃。

## 新增方块要改哪些地方

1. `common/.../registry/ModBlocks.kt`：按现有表格加一项（`block(...)` 或 `glassBlock(...)`）；
2. `common/.../registry/ModItems.kt`：无需改动，`ModBlocks.all` 会自动生成 BlockItem；
3. `common/.../datagen/ModModelProvider.kt`：把 `TexturedBlock("目录/名字")` 加进
   `cubes` / `glassBlocks` / `shapedBases` / `elementBlocks` 中合适的一张表；
4. 纹理放到 `common/src/main/resources/assets/minelzu/textures/block/目录/名字.png`；
5. 语言文件补 `block.minelzu.名字`；
6. 跑 `.\gradlew.bat :neoforge:runData`，再 `git diff common/src/generated` 确认变更。

## 生成结果的校验方式

把 `common/src/generated/resources/assets/minelzu` 与移植前手写的 JSON 做结构比对，
101 个文件逐字段一致；6 个自定义元素模型只相差上述 Blockbench 元数据，
`parent`、`textures`、`elements[].from/to/rotation`、`faces[].uv` 全部一致。
当前一次完整生成写出 110 个文件（含 `.cache` 两个记录文件，不进 jar）。
