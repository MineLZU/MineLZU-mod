# 多平台架构

## 模块划分

| 模块 | 作用 | 关键文件 |
| --- | --- | --- |
| `common` | 全部游戏逻辑、注册表、资源、datagen provider | `common/src/main/kotlin/**`、`common/src/main/resources/assets/minelzu/{lang,textures}`、`common/src/generated/resources/**` |
| `fabric` | Fabric 入口与元数据 | `fabric/src/main/kotlin/**/fabric/MineLZUFabric.kt`、`fabric/src/main/resources/fabric.mod.json` |
| `neoforge` | NeoForge 入口、datagen 触发、元数据 | `neoforge/src/main/kotlin/**/neoforge/{MineLZUNeoForge,ModDatagen}.kt`、`neoforge/src/main/resources/META-INF/neoforge.mods.toml` |

`common` 只依赖加载器无关的 API（vanilla + Architectury API），不含任何 `@ExpectPlatform`，
也不引用 `net.neoforged.*` 或 `net.fabricmc.*` 的类。平台模块在各自的入口里调用同一个
`MineLZU.init()`。

## 入口

```kotlin
object MineLZU {
    fun init() {
        ModBlocks.REGISTER.register()
        ModItems.REGISTER.register()
        ModCreativeTabs.REGISTER.register()
    }
}
```

* Fabric：`class MineLZUFabric : ModInitializer` 的 `onInitialize()` 调用 `MineLZU.init()`。
* NeoForge：`@Mod(MineLZU.MODID) class MineLZUNeoForge` 的构造器调用 `MineLZU.init()`，
  同时把 `GatherDataEvent.Client` 监听器注册到 mod 事件总线。

## 为什么不用 architectury-plugin

官方模板依赖 `architectury-plugin` 的 `transformProduction*` 配置与 dev transformer 做
`@ExpectPlatform` 注入。本仓库用不到这两点：

* 26.3 起 Minecraft 不再混淆，`dev.architectury.loom-no-remap` 直接编译 official 名，
  不需要额外的 remap 流程；
* `common` 里的注册表全部走 Architectury API（`DeferredRegister`、`Registrar`），
  原始项目里唯一的 Fabric 专属代码是渲染层注册，而 26.3 的渲染层由纹理透明度自动决定，
  这段代码已经删除，因此没有任何 `@ExpectPlatform` 需要注入。

去掉 `architectury-plugin` 还顺带解决两个实际问题：

* 它的 dev transformer 在 5.2.91 版本用旧版 ASM，遇到 lwjgl 的
  `META-INF/versions/27`（Java 27 字节码）直接 `Unsupported class file major version 71`；
* 该 transformer 会留下非守护线程池，导致 `runData`、`runClient` 之类的 run 任务
  在游戏结束后永不退出。

代价是平台 jar 的合并要自己做：`fabric`、`neoforge` 各自把 `common` 的产物以非传递方式
shadow 进最终 jar（`shadowBundle(project(path: ':common')) { transitive = false }`），
Architectury API、Fabric Loader、Kotlin 标准库等仍然作为外部依赖声明，不打进 jar。

## loom run 的两处关键配置

```groovy
# neoforge/build.gradle
loom {
    mods {
        main {
            sourceSet 'main', ':common'
        }
    }
    runs {
        data {
            clientData()
            devLaunchMainClass = 'net.neoforged.fml.startup.DataClient'
        }
    }
}
```

* `mods { main { ... } }` 复用 loom 默认的 `main` mod 组并把 `common` 的源集挂进去。
  如果另起一个名字（例如 `mods { minelzu { ... } }`），loom 会同时产出两组
  `MOD_CLASSES` 条目，FML 会看到同 modid 的两个 mod file，选版本更高的那个，
  结果 `common` 的类丢失，运行时报 `NoClassDefFoundError: io/github/minelzu/minelzu_mod/MineLZU`。
* `devLaunchMainClass` 指定真正的游戏主类，绕开 loom 默认的
  `net.fabricmc.devlaunchinjector.Main`。Dev Launch Injector 会把游戏内容放进子类加载器，
  导致 `net.minecraft.server.Bootstrap` 等类被加载两次（父加载器一次、子加载器一次），
  未 bootstrap 的那份副本会抛 `Not bootstrapped`。

`common` 与 `fabric` 的编译目标是 vanilla 未打补丁的 jar，因此 datagen 里不能依赖
NeoForge 的类增强（例如 `ModelProvider.registerModels`、public 的
`BlockModelGenerators.blockStateOutput`）。这些成员通过
`common/src/main/resources/minelzu.accesswidener` 放宽（`official` 命名空间），
再由两个模块的 `loom { accessWidenerPath = ... }` 接线；`fabric.mod.json` 里也声明了
`accessWidener`，生产环境由 Fabric Loader 应用。

## 注册流程

`DeferredRegister.register()` 必须在平台入口的注册阶段调用：

* Fabric：`RegistrarManager` 立即回调，`REGISTER.register()` 直接落到 `Registry.register`；
* NeoForge：`RegistrarManager` 挂到 `RegisterEvent`，由事件回调逐个注册。

方块对象本身是懒创建的（`REGISTER.register(name) { factory(properties) }`），
datagen 阶段注册表已冻结，提前 `new Block(...)` 会抛 `Registry is already frozen`；
属性（`BlockBehaviour.Properties`）也必须在 supplier 内部构造，否则在 datagen 的
bootstrap 之前访问会抛 `Not bootstrapped`。

## 新增方块

1. 在 `common/src/main/kotlin/io/github/minelzu/minelzu_mod/registry/ModBlocks.kt` 里
   按现有表格加一项（`block(...)` 或 `glassBlock(...)`）；
2. 在 `common/.../registry/ModItems.kt` 里一般不需要动，物品由 `ModBlocks.all` 自动派生；
3. 在 `common/.../datagen/ModModelProvider.kt` 的 `cubes`、`glassBlocks`、`shapedBases`、
   `elementBlocks` 之一登记模型；
4. 需要进 `minecraft:walls` 标签的，改 `common/.../datagen/ModBlockTagsProvider.kt`；
5. 加语言键与纹理（这两项手写）；
6. 运行 `.\gradlew.bat :neoforge:runData` 重新生成 JSON。
